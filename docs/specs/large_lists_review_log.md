# Large lists: review log
> Status: plan (spec only, no production code). Spec set: large_lists (see large_lists_README.md).
> Points: 1 to 9. Owner area: review (cross-area). Work packages: all. Decisions: all.

## Purpose

This log records how the plan was produced and challenged: the research, the area designs, five independent review lenses, the revision, the slicing, the final completeness critic and the consolidation. Every review issue is listed with its resolution.

1. Process
2. Review issues and resolutions per lens

## 1. Process

1. **Baseline.** Local replica of the CI workflows: plugin specs on Redmine 5.1, 6.0, 6.1 and 7.0, all 259 examples and 0 failures. RuboCop with the core 7.0 configuration (plugins un-excluded): 107 offenses in 38 files.
2. **Research.** Eight read-only readers mapped Redmine core (5.1, 6.0, 6.1, 7.0), the plugin server side, the frontend, the admin form, the project pages, the API and context menu, the tests and the large-list limits, each with file and line evidence. A completeness critic checked them and resolved the contradictions (for example the HTTP status on Rack's 4,096-parameter limit, and `url_for` in the 7.0 context menu).
3. **Design.** Six area designs: server, frontend, editor, project, limits, quality. They started from the default decisions D1 to D10.
4. **Review.** Five lenses reviewed all designs together: independent senior reviewer, adversarial QA, UX and product consistency, backward compatibility, security and performance.
5. **Revision.** Each area designer resolved every issue tagged for its area, or rejected it with evidence.
6. **Slicing.** A delivery lead cut the revised designs into 32 work packages and four releases, with the compatibility matrix, the perceptible changes, the separately tracked defects and the owner decisions.
7. **Completeness critic.** It found 15 gaps, mostly cross-references and contract details. All were applied during consolidation (section 3).
8. **Consolidation.** The spec set in this directory.

## 2. Review issues and resolutions per lens

Each resolution is quoted in full as the area designer recorded it in the revision step (line breaks joined, pipe characters shown as /). Later steps superseded some of these texts. Where a resolution disagrees with the area designs, the decisions register, the work packages or section 3, those documents win. The main supersessions:

- Failed-save re-render (gap 1): the explicit echo flag (data-dcf-editor-echo) proposed in the R4 resolutions is withdrawn. On both pages the hidden input always renders blank; the parsed ok payload goes into data-dcf-editor-mapping with data-dcf-editor-dirty="1"; there is no data-dcf-editor-echo and no input_value.
- DependencyRules.value_options returns [key, label, active] tuples (gap 3), not the hash shapes proposed in the R7 resolutions.
- storage_preview(custom_field, store), called as format.storage_preview(record, record.format_store), and translate_error(e) (gap 4). Other signatures quoted below (for example translate_error(key, interpolations)) are superseded.
- The i18n constants are ClientConfig::I18N and DependencyEditorConfig::I18N (gap 5). DependencyRules.parent_of(cf) is defined in the server design (gap 2).
- Work package ids without a hyphen (WP0, WP1, WP3, WP4) are the provisional numbering used during revision. The final ids are WP-01 to WP-32 in large_lists_work_packages.md.
- Version targets are normalized to the canonical releases: 0.0.16 = WP-01..WP-07, 0.1.0 = WP-08..WP-14, 0.2.0 = WP-15..WP-20, 0.3.0 = WP-21..WP-32. JS shims and CustomFieldVisibility are deprecated in 0.2.0 and removable no earlier than 0.3.0 (recommended 0.4.0); project nested params are deprecated in 0.3.0 and removable no earlier than 0.4.0.
- Locale texts mentioned in resolutions are historical. The final texts are in large_lists_i18n_registry.md.

### Security + performance reviewer (gates G5/G6)

Scope: I checked the load-bearing claims against the plugin code, the core 5.1 and 7.0 trees, and Rack 2.2.24 and 3.2.7, and measured them. ## 4. Remaining risks

- The point-1 server switch removes the global that the current JS depends on. Server and frontend must land in the same PR and release, or every depending field loses filtering. (server)
- The canonical contract now changes the frontend runtime in three places: the parent-values replacement for data-dcf-allowed, the required-none option rule, and no attributes on unmanaged fields. The frontend design must be revised to match before WP-16/WP-17 start (done in consolidation). (server)
- Reading @copied_from relies on a core instance variable with no public reader. It is stable in 5.1..7.0 (verified) and pinned by a spec on all four versions, but a future core refactor could rename it. Copies would then fall back to strict validation (today's behaviour), not to a crash. (server)
- Leniency (per-value D1, copies, non-editable children) lets stored invalid combinations persist. That is intended so they do not block edits; data hygiene depends on users changing values or an optional report. (server)
- Treating fields in or below a stored cycle as unconstrained relaxes validation for those legacy configurations until an admin fixes the cycle. The admin warning makes it visible. (server)
- The size budget for the context menu may be exceeded on installations with several very large wizard children. The lazy wizard body is a user decision, not in the default plan. (server)
- The FieldIndex regex depends on Psych writing top-level store keys at column 0. A deserialization fallback covers other emitters, but third-party code writing format_store with another YAML emitter would pay the parse cost. (server)
- The record-scoped memo (dcf_memo) can be stale if a chain member changes later in the same request. Admin saves do not use it; documented. (server)
- The reimplemented bulk_edit_tag branch (required managed children only) can drift from core. A drift spec compares the non-required path with core output on all versions. (server)
- Third-party code calling the removed MappingBuilder/ParentMenuBuilder or reading the removed globals breaks. None was found in public code. (server)
- Locale parity tooling must flatten nested activerecord keys and detect duplicate keys, or collisions across areas stay invisible. (server)
- Cross-area decisions recorded in section 20 (payload, editor DOM, audit, storage UI, generator, flash escaping) are proposals for other owners. If an owner area chooses differently, the consolidated plan must reconcile it before implementation. (server)
- Contract drift between ClientData and the runtime. Mitigated by the request-based fixture spec in every version workflow, a jsdom outcome test per fixture, and one release for the JS and server changes. (frontend)
- Legacy handling relies on server D1 per value and on value_was semantics. If the server keeps whole-set leniency, multi-child edits with legacy values fail validation. (frontend)
- D2 revision: issues whose kept child is invalid under the new parent are reported as per-issue bulk failures instead of being cleared silently. Users must then set the child explicitly. This is the intended trade-off against data loss. (frontend)
- Visibility-gated emission costs a role check for role-restricted parents (visible? short-circuits otherwise). The server must memoize to keep the G6 query invariance. (frontend)
- Browsers that ignore hidden on option show disallowed options greyed out; disabled still prevents picking them. (frontend)
- select2-like overlays ignore option.hidden. Other overlays need an integrator hook on dcf:updated. (frontend)
- Third-party scripts or themes relying on the disabled child control, the always-fired change event, the mirror inputs or data-depending-* attributes behave differently (none found publicly). (frontend)
- Large mappings: data-dcf-map is repeated per rendered child and per wizard field. Integer enumeration ids help; very large lists should use depending_enumeration. (frontend)
- jsdom is not a CSS or performance oracle. The [hidden] overrides for em.info and .check_box_group label need the opt-in system specs. (frontend)
- Initialising inside the MutationObserver callback runs the initial evaluation synchronously in the microtask after large insertions. It is cheap per field, but a page with many depending fields pays it in one go. (frontend)
- A stale cached old script with the new markup leaves fields unfiltered and breaks the wizard save until reload. Documented in the Upgrade notes. (frontend)
- Explicit fixture ids in a reserved range: a future core test fixture in that range would collide. The range is far above any id used in Redmine test fixtures, and the self-check would fail loudly. (frontend)
- The pre-existing wizard save authorization defect (SP-07) remains until its separately tracked fix lands. It must ship no later than the release that ships point 1. (frontend)
- Admins and project managers without JavaScript can no longer edit mappings (admin: unchanged on save; project: Save disabled). The JSON API and jc-redmine_extended_api remain JS-free paths for admins only. (editor)
- Switching the core admin form to multipart/form-data is a new interaction with core. It is verified at the Rack level (rack 2.2.24 and 3.2.7) and covered by a request spec and the opt-in system spec, but other plugins that read form.enctype or post the form themselves were not surveyed. (editor)
- Very large fields still ship full data attributes (parent values, enumeration child values, mapping): megabytes at 5,000 x 25,000 although the DOM is lazy. The editor is bounded by the 4 MiB payload cap and about 15.5 MiB per form; reverse proxies with default limits (nginx 1 MB) cut earlier and the pre-check cannot detect them. (editor)
- jsdom is not a browser: toggle timing, focus, the [hidden] versus em.info rules, real multipart submission and real-browser performance need the opt-in system spec and manual checks. (editor)
- Enumeration import by name makes export-then-import fail on duplicate names (active or inactive) until the values are renamed. (editor)
- Formula protection is opt-in and off by default (core parity). Exports of values entered by project managers can still execute cells starting with = + - @ in a spreadsheet unless the admin protects them; the help text warns. (editor)
- The stale check is not atomic: a write between the digest comparison in before_validation and the commit is not detected (no row lock). (editor)
- The conflict panel offers use, keep or export but no three-way merge, so a user who wants to combine both versions must do it by hand (the export helps). (editor)
- Orphan links persist, inert, until the editor is next saved dirty, because untouched saves never prune by design (BC-02). (editor)
- Cross-area dependencies: server prune_mapping (contract in section 2.2), value_options tuples and the head hook asset list; limits StorageLimits API names and the field_value_dependencies label; project integration per section 7. Drift is caught by the endpoint/presenter contract spec, the payload contract spec and the locale duplicate-key check. (editor)
- Two MutationObservers (issue-form runtime and editor) are active on admin pages; editor re-renders stay single-fragment appends. (editor)
- The count-agnostic phrasing ('Label: %{count}') is grammatical but less natural; de, fr and nl texts should be reviewed by native speakers. (editor)
- Cross-area contract drift remains the main risk. This design depends on editor additions (submit gate, max payload attribute, pending state, schema v1 with import) and limits additions (effective_limit, dcf_storage_ceiling, Violation#source, payload_sha256 marker name, README-free service texts). Mitigation: section 2 pins them; T-DEPJ-15/16/19/21 and the shared fixtures fail on drift. (project)
- Point-1 ordering: until Rails.cache.delete_matched is removed from the formats' after_save, every project save of a depending field (sort and cascades included) is a 500 on MemCacheStore. Land point 1 first. Resolved by ordering: WP-03 removes delete_matched in 0.0.16, before any project WP (0.3.0). (project)
- The project storage ceiling is a new refusal on PostgreSQL/SQLite. Fields an admin made larger than the ceiling can still shrink or keep their size, but cannot grow, through project pages. The default (2,048 KiB) and its exposure as a setting are listed for owner confirmation. (project)
- The 255-character cap for new list values at project level is a new rule. Existing longer values are untouched. (project)
- Managers without JavaScript can no longer change mappings at project level (Save disabled). (project)
- Reverse proxies (nginx client_max_body_size, 1 MB by default) can reject large mapping saves with a 413 before Rails. Documented; not detectable by the plugin. (project)
- The long-number guard costs up to about 0.2 s on a 4 MiB digit-dense payload, comparable to JSON.parse itself, on an authenticated manager path. (project)
- The enumeration sort uses update_all (no validations). It is safe today because CustomFieldEnumeration has no update callbacks in 5.1 to 7.0; a future core callback would be bypassed. (project)
- source and import in the audit are client-reported. They are documented as informational; only the server-computed delta and digests are authoritative. (project)
- Lists over 500 values lose drag-and-drop; move-to-position is a follow-up. (project)
- The default-value select still lists every value (about 250 KB at 5,000 values). (project)
- Exact measurement depends on the point 6 owner using the same sanitize-only normalizer in storage_preview and before_custom_field_save, and on the transport areas decoding dependencies_json in before_validation or inside the service. Mitigated by the 'preview equals stored bytes' and no-prune specs. (limits)
- Behaviour change on non-strict MySQL: saves that used to 'succeed' with silent truncation now fail. Owners must widen the columns or reduce the lists (Upgrade note). (limits)
- After widening, max_allowed_packet becomes the real ceiling (MySQL 5.7 default 4 MB). Mitigated by the MEDIUMTEXT default, the 4 MiB transport cap, and the widener and report warnings. (limits)
- Running processes keep the old 65,535 limit until restart. This is safe but can confuse; it is documented in the task output and the README. (limits)
- Fields already corrupted by past non-strict truncation cannot be opened. Recovery needs a backup restore; report_sizes detects them. (limits)
- ALTER TABLE on custom_fields takes a metadata lock, which on Galera briefly blocks writes cluster-wide. (limits)
- Each changed large column costs about two extra YAML dumps per admin save (about 1 s at 5,000 x 25,000). (limits)
- The FieldIndex regex assumes Psych emits top-level keys at column 0. The deserialize fallback covers other shapes. (limits)
- Audit consumers reading after_value above 16 KB see a shrunk value with payload_* markers. No in-plugin view renders these columns. (limits)
- The consolidated design touches files owned by other areas (CustomFieldValidationPatch hosts editor bodies; project delta caps; OperationError kwargs). The work packages must land in a coordinated order: StorageLimits and the patch module before the editor transport. (limits)
- Only MariaDB 10.11 was run. MySQL 8.0 uses the same adapter and SQL but names the isolation variable transaction_isolation. (limits)
- The client estimate uses measured JSON-to-YAML ratios and can be off by about 10 percent. It is advisory only. (limits)
- The canonical contract section changes other area designs; the consolidated plan must apply them: frontend drops data-dcf-allowed and role=status hints (FD-5, FD-14) and reads data-dcf-parent-values; server renames context edit to form, uses the dcf-i18n meta and text_dcf_hint_* keys, adds the radio sentinel, resolves parents from loaded objects, adopts per-value D1, and drops its StorageLimits API, Graph and dcf_too_large; limits withdraws map pruning (L11), renames the audit marker to payload_sha256 and keeps normalization sanitize-only; project drops DependencyEditorData, the pre-filled hidden input, guard_storage!, the 60 KB audit cap and content_for editor assets; editor accepts the import key, the 63-bit/pre-scan rules and the failed-save re-render rule (hidden input blank, posted payload in data-dcf-editor-mapping with data-dcf-editor-dirty="1"; the echo flag is withdrawn, gap 1). If any area keeps its old shape, the generated fixtures and golden files fail by design. (quality)
- Selenium Manager needs network access on first use; offline machines need a matching CHROME_BIN + chromedriver pair, otherwise the system suite is NOT RUN. A chromedriver 147 on /opt/node22/bin breaks sessions unless stripped from PATH. (quality)
- Local Ruby patch levels (3.2.6/3.3.6) differ from CI (3.2.5/3.3.9/3.4.5); Ruby 3.4-specific breakage on 7.0 is caught only by CI or a local 3.4. (quality)
- A count-based ratchet can miss an offense swap within one file and cop; reviewers must read the diff. RuboCop follows core 7.0-stable (~> 1.88); base and head always use the same version. (quality)
- Explicit fixture ids bump InnoDB AUTO_INCREMENT past the fixed range even after rollback on MySQL; harmless for this suite but visible in the optional MariaDB run. (quality)
- Version-specific markup differences (icons, propshaft) may require per-version fixture variants; each variant must be regenerated deliberately and reviewed. (quality)
- jsdom fidelity gaps (FormData includes disabled selected options, no CSS.escape, no CSS cascade, slow option writes) can give false confidence; system specs cover them but are opt-in, so a UI WP must run them or it is not DONE. (quality)
- Every system example costs about 5 s; the scenario list must stay small. (quality)
- rspec-61.yml and js-tests.yml are dispatchable only once they exist on the default branch. (quality)
- The --db mysql path of test_setup.sh is designed but not prototyped here; MariaDB evidence comes from the limits area's runs. (quality)
- The compat grep can produce false positives; the dcf-compat-ok marker must be used sparingly and is visible in review. (quality)
- A base file that did not parse under Ruby 2.7 resets the ratchet baseline for that file; only the INFO line and review catch new style offenses there. (quality)
- jsdom must stay ~29.1.1 on Node 22.22.0; a jsdom bump must be deliberate. (quality)
- The G6 differential checks rely on core loading custom field roles on the same instances the plugin reuses (verified on 5.1 and 7.0, E22); a core change that reloads instances would show up as a failing invariance spec, which is the intended signal. (quality)
