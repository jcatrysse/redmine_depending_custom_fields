## 1. Purpose

This document is the single source of truth for every locale key that the large_lists plan adds, changes, reuses on purpose or removes in `config/locales/{de,en,fr,nl}.yml`. It resolves critic gaps 8 (no consolidated registry, colliding keys, keys without an owner WP), 9 (UX-16 corrections and per-locale quotes) and 10 (parity allowlist).

- Every new key has exactly one owner WP. The owner adds the key to all four locale files in one commit, with the texts of section 4 copied verbatim. Every other WP reuses the key and never redefines it.
- The area documents (`large_lists_server_design.md` section 15, `large_lists_frontend_design.md` section 3.6, `large_lists_editor_design.md` section 9, `large_lists_project_design.md` section 11, `large_lists_limits_design.md` section 11, `large_lists_quality_protocol.md` section 2.7) keep key names, owners, interpolations and JS keys only. Where any of them, or the revision 2 tables in `$S/design_out/design_*.md`, shows a different text, this registry wins.
- Releases follow the work packages: 0.0.16 = WP-01..WP-07, 0.1.0 = WP-08..WP-14, 0.2.0 = WP-15..WP-20, 0.3.0 = WP-21..WP-32. A key ships in the release of its owner WP.
- The per-WP report (quality protocol section 7, gate G8) contains a `key | owner | en | de | fr | nl` table for the keys the WP adds; it must match this registry cell for cell, plus the native-speaker review line for de, fr and nl.

`$S` = `<planning scratch space, not part of the repository>`.

## 2. Rules

**Parity.** Redmine falls back to `en` for a key missing in the current locale, so a missing de, fr or nl entry would not break a page. The plugin still keeps de, en, fr and nl at strict parity: the same flattened key paths in all four files (nested `activerecord.errors.messages.*` included), enforced by `spec/quality/locale_parity_spec.rb` (WP-02, gate G8). A value identical to `en` is allowed only when it is listed in the parity allowlist (section 6).

**Interpolation.** Interpolation names are identical across the four languages for every key (same set of `%{name}` tokens; order may differ). No locale adds, drops or renames a variable. The parity spec compares the sets per key.

**Quotes around placeholders and quoted labels.**
- en and nl: ASCII double quotes, for example `"%{value}"`. In YAML they are escaped (`\"`) inside the double-quoted value, or the value is single-quoted; the parsed string must equal the registry text.
- de: German quotes „…“ (U+201E opening, U+201C closing), for example `„%{value}“`. No ASCII double quotes in de values.
- fr: guillemets « … » with a plain space inside, as in core fr (`text_enumeration_destroy_question`), for example `« %{value} »`. No ASCII double quotes in fr values.
- The WP-02 quote check applies these rules to every value of every locale file.

**Dashes.** No en dash (U+2013) or em dash (U+2014) in any locale value, nor in README.md and CHANGELOG.md. Use a comma, a colon, a semicolon, parentheses or a plain hyphen-minus (`A-Z`, `Drag-and-drop`, `UTF-8`). Checked by `spec/quality/no_dash_spec.rb` (WP-02).

**Typography per locale.** fr puts a plain space before `:`, `;`, `?` and `%` (as the existing plugin fr file does); de writes `93 %` with a space; en and nl write `93%`. Ellipses are three ASCII dots (`...`).

**Plurals.** No key in this registry uses plural subkeys. Counts are phrased as "Label: %{count}" or as a parenthesised number, so no word agrees with the count. A future key that cannot avoid agreement uses `one`/`other` subkeys in all four locales (fr may add `zero`), as the G8 parity spec allows.

**Glossary** (from the existing plugin files and quality section 2.7):

| Term | de | fr | nl |
|---|---|---|---|
| custom field | benutzerdefiniertes Feld | champ personnalisé | aangepast veld |
| parent / child (value, field) | übergeordnet / untergeordnet | parent / enfant | bovenliggend / onderliggend |
| (depending) | (abhängig) | (dépendante) | (afhankelijk) |
| dependency mapping | Abhängigkeitszuordnung | mappage des dépendances | afhankelijkheidskoppeling |
| link (one parent/child pair) | Verknüpfung | lien | koppeling |
| ask an administrator | wenden Sie sich an einen Administrator | contactez un administrateur | vraag een beheerder (om hulp) |
| possible values | mögliche Werte | valeurs possibles | mogelijke waarden |

**YAML layout.**
- Values are double-quoted, as in the existing files. A value that starts with `%{` or contains `: ` must be quoted anyway.
- Nested keys live under ONE `activerecord:` / `errors:` / `messages:` block per locale file. WP-10 creates the block with `dcf_circular_dependency`; WP-11 and WP-22 add their keys inside that same block. A second `activerecord:` mapping in the same file is a duplicate mapping key and fails the WP-02 Psych tree walk.
- Flat keys are appended once; a key that already exists is reused, never written a second time (the duplicate-key check fails otherwise).

**Constant maps.** Keys that reach JavaScript do so only through `RedmineDependingCustomFields::ClientConfig::I18N` (meta tag `dcf-i18n`, WP-18) and `DependencyEditorConfig::I18N` (`data-dcf-editor-i18n`, WP-24 to WP-26). The name `I18N_KEYS` is not used anywhere. The WP-02 parity spec resolves every value of both maps, each when it is defined, in all four locales with `raise: true`; WP-18 and WP-24 each add an example proving their map is checked.

**JavaScript fallbacks.** The issue-form runtime's built-in English fallback texts (used when the meta tag is missing or invalid) equal the `en` column of the WP-18 keys byte for byte.

## 5. Landing rules for shared keys and constant maps

- **`text_dcf_no_matches`** (critic gap 8). Owner WP-28. WP-28 does not depend on WP-25, so either may merge first. Whichever of WP-25 and WP-28 merges first adds the key to the four locale files with the registry text; the later one reuses it and adds nothing to the locale files. WP-25 adds the `no_matches` entry to `DependencyEditorConfig::I18N` in either order, so when WP-25 merges first it must also add the locale entry in the same commit (every map value resolves at every commit). Both WPs ship in 0.3.0.
- **`error_invalid_dependency_payload`, `error_dcf_dependencies_too_large_to_send`.** Owner WP-25. WP-27 uses them on the project page and redefines neither (WP-27 depends on WP-25).
- **`text_dcf_editor_help`, `text_dcf_editor_noscript`.** Owner WP-24. The project page (WP-27) reuses them; `text_dcf_editor_help` replaces `text_dependency_matrix_help` there.
- **`text_dcf_storage_estimate`.** Owner WP-24 (text designed by the limits area); WP-25 shows it and reuses the key.
- **`field_value_dependencies`.** Owner WP-11. WP-22 (payload errors), WP-24 and WP-25 (legend, estimate label) reuse it; the server and editor areas do not define it.
- **`DependencyEditorConfig::I18N`.** WP-24 creates the map with entries for its own keys only (at least `storageEstimate`). WP-25 and WP-26 extend it in the same commit as their locale entries, with the JS keys named in the "used by" column and in `large_lists_editor_design.md` section 9, plus the reused core keys of section 8.3 (WP-25: `collapse_all`, `clear`, `default_value`, `unsaved`, `no_default`; WP-26: `export`, `preview`, `separator`, `comma`, `semicolon`, `yes`, `no`, `status`).
- **`ClientConfig::I18N`.** WP-18 creates it with exactly 10 entries: the nine WP-18 keys and the existing `error_save_failed` (`saveFailed`).
- **Nested block.** The single `activerecord.errors.messages` block per file is created by WP-10 (0.1.0) and extended by WP-11 (0.1.0) and WP-22 (0.3.0).
